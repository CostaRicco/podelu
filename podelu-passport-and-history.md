## 1. Суть продукта

Сервис учёта клиентских работ и поддержки для digital-проектов:

- клиенты и их внутренние заметки;
- направления работ (Сайт, 1С, произвольные);
- месячные пакеты часов: разовые и абонентские (повторяющиеся), с общим балансом на несколько направлений;
- задачи (работы) и записи затраченного времени (выполнения);
- остатки по пакетам без переноса между месяцами;
- общий журнал работ по всем клиентам и карточка отдельного клиента;
- шаблоны быстрых работ (созвон, доработка, исправление, тестирование, своя работа).

Не реализовано: отдельный клиентский доступ, вложения, таймер, уведомления, аудит изменений, автоматический deploy [код].

Доступ: только администратор Битрикса. Каждый экран и каждое действие проверяют вход и IsAdmin [код].

Хранение: Highload-блоки (HL). Каждая сущность это HL-блок с таблицей mc_podelu_* и полями UF_* [код].

## 3. Модель данных (схема 1.8.0)

Во всех сущностях ID это автоинкремент HL. Время хранится целыми минутами. Месяц это строка YYYY-MM. Дата это строка YYYY-MM-DD [код].
UF_XML_ID: внешний идентификатор. Для задач и выполнений в нём хранится ключ идемпотентности (WORK_<токен>, TIME_<токен>).

### 3.1 McPodeluClients (mc_podelu_clients)

| Поле | Тип | Смысл |
|---|---|---|
| UF_NAME | string 150, обязательное | Название клиента |
| UF_SITE | string 255 | Сайт, только http/https без логина и пробелов |
| UF_COMMENT | string 3000 | Внутренняя заметка |
| UF_ACTIVE | boolean | Активность |
| UF_CREATED_AT, UF_CREATED_BY | datetime, integer | Создание, ID пользователя Битрикса |
| UF_XML_ID | string 64 | Внешний ID |

### 3.2 McPodeluDirections (mc_podelu_directions)

UF_NAME (100, обязательное, уникально без учёта регистра), UF_ACTIVE, UF_XML_ID. Начальные значения: «Сайт» (MC_SITE), «1С» (MC_1C) [код: install.php].

### 3.3 McPodeluPackages (mc_podelu_packages)

| Поле | Смысл |
|---|---|
| UF_CLIENT | ID клиента |
| UF_MONTH | Первый месяц для абонентского или единственный для разового |
| UF_NAME | Базовое название |
| UF_MINUTES | Базовый лимит в минутах (ввод в часах, шаг 0,25 ч) |
| UF_DIRECTION_IDS | JSON-массив ID направлений: один общий баланс на все перечисленные |
| UF_REPEAT | 1 = абонентский (каждый месяц) |
| UF_END_MONTH | Последний месяц включительно, пусто = без окончания |
| UF_CREATED_AT, UF_CREATED_BY, UF_XML_ID | Служебные |

### 3.4 McPodeluPackageRules (mc_podelu_package_rules)

Изменения условий абонентского пакета: UF_PACKAGE, UF_MONTH, UF_SCOPE (one = только месяц, from = с месяца и далее), UF_NAME, UF_MINUTES, UF_DIRECTION_IDS, UF_CREATED_AT, UF_CREATED_BY.

### 3.5 McPodeluPackageSkips (mc_podelu_package_skips)

Исключение месяца из абонентского пакета: UF_PACKAGE, UF_MONTH. Исключённый пакет показывается, но его лимит и остаток считаются нулевыми.

### 3.6 McPodeluTasks (mc_podelu_tasks): работы

| Поле | Смысл |
|---|---|
| UF_CLIENT, UF_DIRECTION | Клиент и направление (направление нельзя менять, если есть выполнения) |
| UF_NAME (180), UF_DESCRIPTION (5000), UF_NOTE (5000) | Название, описание, внутренняя заметка |
| UF_STATUS | planned, work, done |
| UF_MONTH | Плановый месяц |
| UF_DONE_MONTH | Месяц завершения (ставится при переходе в done) |
| UF_TEMPLATE_ID, UF_TEMPLATE_GROUP | Шаблон и признак общей группы (созвоны) |
| UF_REQUEST_HASH, UF_XML_ID | Хеш запроса и ключ WORK_<токен> для идемпотентности |

### 3.7 McPodeluTime (mc_podelu_time): выполнения

UF_TASK, UF_CLIENT, UF_DIRECTION (копия направления задачи), UF_PACKAGE (0 = без пакета), UF_DATE, UF_MINUTES (1..1440),
UF_DESCRIPTION (3000), UF_NOTE (5000), UF_REQUEST_HASH, UF_XML_ID (TIME_<токен>), UF_CREATED_AT, UF_CREATED_BY.

### 3.8 McPodeluWorkTemplates (mc_podelu_work_templates)

UF_NAME (пункт меню), UF_TITLE (название работы/группы), UF_DESCRIPTION, UF_DIRECTION (0 = выбирать при добавлении),
UF_DURATIONS (JSON, 1 до 6 значений от 1 до 1440 минут), UF_GROUP, UF_ACTIVE, UF_FAVORITE, UF_SORT, UF_ICON (phone, tool, bug, test, plain), UF_XML_ID.
Начальные: Созвон (MC_CALL, группа), Доработка (MC_CHANGE), Исправление (MC_FIX), Тестирование (MC_TEST) [код: install.php].

### 3.9 Связи и целостность

Внешних ключей SQL нет. Целостность держит приложение через Repository [код]. Не правьте связанные записи вручную в технической админке.
Версия схемы хранится в опции markitan.podelu / schema_version и сверяется при каждом запросе (ожидается 1.8.0).

## 4. Бизнес-правила (обязательны для любого внешнего API)

1. Календарный месяц. Неиспользованные часы и перерасход не переносятся [код].
2. Фактическое время: целые минуты, от 1 минуты до 24 часов за запись. 40 минут не округляются до 45 [код].
3. Договорные лимиты: часы с шагом 0,25, внутри хранятся минутами; максимум 99999,75 ч [код].
4. Действующие условия абонентского пакета в месяце M: база, затем последнее правило from не позже M, затем правило one ровно на M. Разовый пакет существует только в UF_MONTH [код: Policy.php].
5. Баланс клиента за месяц: limit (сумма лимитов не исключённых пакетов), spent (всё время месяца), extra (время без пакета), packageSpent = spent минус extra,
   free (сумма положительных остатков), over (сумма перерасходов), count. Перерасход одного пакета не гасится остатком другого [код: Policy::balance].
6. Работа без пакета (UF_PACKAGE = 0) не уменьшает лимит [код].
7. Пакет подходит записи, только если он действует в месяце даты и содержит направление задачи [код: timeRaw].
8. Нельзя изменить, завершить, исключить или сделать недействительным пакет так, чтобы учтённое время осталось без подходящего пакета [код: checkTime].
9. Пакет с временем нельзя удалить. Задачу с выполнениями нельзя удалить. Выполнение удаляется отдельно, минуты возвращаются в баланс [код].
10. Первое выполнение переводит задачу planned в work. Завершение (done) запоминает месяц [код].
11. Шаблон с UF_GROUP объединяет выполнения в одну открытую (не done) группу по клиенту, шаблону и направлению. Старые похожие задачи автоматически не объединяются [код: saveWork].
12. Группа без выполнений в выбранном месяце не показывается, но остаётся в базе [код].
13. Журнал месяца показывает задачу, если она запланирована на месяц, не завершена и запланирована не позднее него, завершена в нём, либо имеет выполнения в нём [код: works.php].

## 5. Идемпотентность и параллельность

- Все записи по клиенту идут в одной транзакции InnoDB с блокировкой строки клиента (SELECT ... FOR UPDATE) [код: tx()].
- Создание работы и первого выполнения атомарно. Ключ запроса: 32 hex-символа в поле request.
- Повтор с тем же ключом и теми же данными возвращает прежний результат. Тот же ключ с другими данными отклоняется ошибкой [код].
- Для обычного создания клиента, направления, пакета и шаблона идемпотентности нет: повтор создаст дубль (кроме проверки названия направления) [код].
- Полного аудита нет. При параллельном редактировании одной записи выигрывает последнее сохранение [код].

## 6. Текущие HTTP-обработчики (браузерные, не API)

Критически важно для MCP: все обработчики рассчитаны на сессию администратора Битрикса и CSRF-токен sessid.
Чтение данных отдельным JSON-API не существует: view.php возвращает готовый HTML внутри JSON [код].
Поэтому внешний MCP не должен ходить в эти обработчики. Нужен новый серверный слой (см. раздел 9).

### 6.1 Защита [код: bootstrap.php]

- Не вошёл или не администратор: 403 JSON.
- Не POST там, где нужен POST: 405. Неверный sessid: 403.
- Заголовки Cache-Control: no-store, private и X-Content-Type-Options: nosniff.

### 6.2 action.php: POST, поле action

Ответ при ajax=Y: {success, message, redirect, ...}; 422 для ошибок проверки, 500 для сбоев хранилища, 403 для доступа.
Поля общие: id, client, month, context, return, ajax, sessid.

| action | Основные поля | Эффект |
|---|---|---|
| client | name, site, note, active | Новый клиент |
| direction | name | Новое направление |
| preset | id, name, title, description, direction, durations, group, favorite, active, sort, icon | Создать или изменить шаблон |
| package | id, client, month, name, hours, directions[], repeat, end, scope | Создать или изменить пакет, правило one/from |
| end | id, client, end, month | Последний месяц абонентского пакета |
| manage | id, client, month, mode (finish, skip, restore, delete, clear), confirm | Управление пакетом; delete требует слово УДАЛИТЬ |
| work | client, task, planned, name, direction, status, month, date, hours, minutes, package, description, note, request, preset | Новая работа с первым выполнением, либо выполнение в существующей задаче, либо плановая работа |
| time | id, client, task, date, hours, minutes, package, description, note, request | Изменение выполнения |
| task | id, client, name, description, note, direction, status, month | Свойства задачи |
| deleteTask | id, client, month | Удалить задачу без выполнений |
| deleteTime | id, client, month | Удалить выполнение |

### 6.3 Остальные [код]

- options.php (POST): client, direction, date, task. Возвращает подходящие пакеты {id, name, minutes}.
- view.php (GET): url (только из белого списка маршрутов), fragment (page или form). Возвращает HTML.
- install.php: установщик/миграция; после установки удаляется. Не для MCP.

## 8. Известные ограничения и риски текущей системы

1. Нет JSON-API чтения. Внешний клиент не может получить данные без разбора HTML.
2. Нет персональных токенов и ролей: единственная роль это администратор Битрикса.
3. UF_CREATED_BY хранит ID пользователя Битрикса. Для внешней интеграции нужен выделенный сервисный пользователь или явная отметка источника.
4. Нет журнала аудита. Для работы ИИ-агента через MCP это существенный пробел.
5. Repository::rows() читает таблицы без пагинации; журнал фильтруется в памяти. Для больших объёмов нужна оптимизация.
6. Фильтр месяца по строке даты (с 01 по 31) работает для строковых дат YYYY-MM-DD, но зависит от формата данных.
7. Месяц завершения задачи ставится по серверной дате (date('Y-m')) и зависит от часового пояса PHP.
8. Идемпотентность есть только у работы и выполнения.
9. Клиентский (внешний) доступ, вложения, таймер, уведомления не реализованы.
10. Репозиторий публичный: проверьте, что в нём нет паролей, ключей и реальных данных клиентов. Для будущего MCP не размещайте туда токены и конфигурацию доступа.
11. PHP, миграции и SQL ни разу не запускались в среде сборки: возможны ошибки, видимые только на хостинге.
12. Внешние зависимости интерфейса: CDN jsDelivr (Medeo, GSAP). Для строгой CSP нужны разрешения или локальные копии.

## 9. Требования к будущему MCP-серверу

Решение для проектирования, не реализованная функциональность.

### 9.1 Принципы

- Не использовать сессию администратора и sessid. Новый защищённый API поверх существующих Repository и Validation, чтобы бизнес-правила не дублировались.
- MCP-сервер выступает ресурсным сервером OAuth 2.1: проверка токена на каждом запросе, проверка аудитории (токен выдан именно для этого сервера), запрет передачи полученного токена дальше (token passthrough). Токены не передаются в строке запроса.
- Минимальные права (scopes) по уровням: чтение, запись времени и работ, управление пакетами, удаление. Список инструментов может зависеть от выданных прав.
- Проверка заголовка Origin, HTTPS, ограничение частоты вызовов, проверка всех входных параметров, очистка выходных данных.
- Человек в цикле для необратимых и дорогих действий (удаление, изменение условий пакета).
- Каждый вызов записи содержит ключ идемпотентности. Сервер возвращает прежний результат при повторе.
- Журнал аудита: кто (клиент MCP, пользователь), что, когда, входные данные без секретов.
- Ошибки проверки возвращать как результат инструмента с признаком ошибки, чтобы модель могла исправить вызов; нарушения протокола как ошибки протокола.

## 10. Глоссарий

- Пакет: месячный лимит часов на одно или несколько направлений.
- Абонентский пакет: повторяется каждый месяц, условия меняются правилами one и from.
- Правило one/from: изменение только месяца либо с месяца и далее.
- Выполнение: запись времени внутри задачи (работы).
- Группа созвонов: одна открытая задача на клиента, шаблон и направление, куда складываются выполнения.
- Баланс: расчёт лимита, потраченного, свободного и перерасхода за месяц.
- Ключ запроса (request): одноразовый токен формы для защиты от дублей.

- Спецификация MCP: инструменты (версия 2026-07-28), требования к проверке входных данных, управлению доступом, ограничению частоты вызовов и подтверждению человеком.
- Рекомендации MCP по безопасности: подмена доверенного посредника, передача токена насквозь, перехват сессий, минимизация прав.
